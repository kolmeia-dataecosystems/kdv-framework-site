# Community and guardianship

Open proposals, guardian approval and publication from main.

## Purpose

Anyone can read this repository, open a question, fork it and propose a pull request. Publication into main requires the configured guardian review and passing checks. Repository write access is not required to propose knowledge. Contributor examples must be synthetic or appropriately anonymised.

## Initial guardians

Initial guardian: @ismael-lab. Guardian identity is recorded in CODEOWNERS. With one guardian and no bypass, a pull request authored by that same guardian requires another authorised guardian before it can be approved; self-approval is not a substitute for review.

## Contribution flow

1. Open an issue with the context and proposed improvement.
2. Edit the Markdown in a fork or a permitted working branch.
3. Keep language editions and diagrams consistent; explain any translation gap.
4. Open a pull request with rationale, evidence and limitations.
5. The guardian reviews content and required checks; new changes invalidate stale approval.
6. A guardian merges the accepted change into protected main.
7. The website imports a pinned snapshot of main; the published source revision is displayed with each guide.

## Knowledge publication

The website reads a versioned snapshot of the approved main branch, not a contributor branch. Its maintainers run the documented knowledge synchronization and site release. Reading, editing and publishing are separate steps. A contribution appearing in a pull request is not automatically part of the published framework.

## Release and review boundaries

This proposed edition is visible in a review preview only. It does not replace the published v1.0.0 baseline. Anyone can propose a change; only an accepted protected-main revision can become an official framework release. Website and framework versions remain independent.
